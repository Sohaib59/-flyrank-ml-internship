01 · Title & Abstract

Abstract

Question: which safe, observable content and search signals are associated with a page's visibility, click-through, and short-term movement — and can a simple, honest model turn that association into a better review queue than a fixed rule alone? Method: using one mid-panel month (2026-03) of FlyRank's pseudonymized daily performance and content-metadata tables, a five-feature signal set (impressions, clicks, CTR, average position, word count) was checked for two flag-linked signals, encoded into a transparent baseline rule, then compared against a Logistic Regression model under a client-grouped validation split, with an explicit leakage audit. 02 · Introduction

The decision this work supports

FlyRank's reviewers can only look at a fraction of the content inventory in any given cycle. The question this project answers is not "what will happen to this page" — it's narrower and more honest: given limited review time, which pages are worth a human looking at first?

Two observable, flag-linked signals anchor the analysis: staleness (time since a page's last update — the signal behind FlyRank's existing refresh flags) and CTR relative to a page's position tier (the signal behind FlyRank's existing CTR-fix logic). Rather than trust either on faith, both are checked against real outcomes before they're allowed into a scoring rule. The project then asks whether a small, interpretable model can beat that transparent rule on the same data and the same metric — and if it can, by how much, and at what cost to interpretability.

This is a decision-support project, not a prediction guarantee: the output is a ranked list for a human reviewer, with reasons attached, not an automated action.

Time window used: the full calendar month of 2026-03 — a mid-panel month, deliberately not the release's final month (2026-06), which was treated throughout as a sealed test slice and never used to iterate on feature or label logic.

What was excluded, and why

No FlyRank product decision output (health_score, priority_score, action_type) is used anywhere in this project — these are not shipped in the release and were never reconstructed as features, precisely so that any signal found here is discovered from observed measurements rather than copied from an existing rule. Raw query, URL, and title fields are excluded throughout, and no output in this paper contains anything more specific than a pseudonymized ID or an aggregate statistic.

04 · Methodology

Assumptions, features, label, baseline, validation

Label

The working label is trend_direction == 'down', read at the end of the March window. This is a same-window proxy, not a validated future outcome — it is used consistently, and flagged as a limitation, rather than treated as a strong causal target. A stronger future version of this project would define the label as a forward-looking window (features from March, outcome in April), which was scoped out here to keep the feature and label pipeline stable across all weekly notebooks.

Features (five, each knowable at the decision moment)

Baseline

A transparent rule: baseline_action_score = 0.5 × staleness_norm + 0.5 × ctr_gap_norm, applied only to pages with impressions_30d ≥ 250. Reason code: stale_underperforming_ctr. Action: review_for_refresh. Any signal whose check above did not come back CONFIRMED had its weight set to zero and the remainder renormalized, rather than kept on faith.

Model

Logistic Regression, chosen for interpretability (coefficients read directly as effect direction/size, cross-checked with permutation importance), with Random Forest evaluated as a complexity check — kept only if it clearly beat Logistic Regression on the decision-relevant metric, not by default.

Validation design

Client-grouped split (GroupShuffleSplit on client_hash_id, 75/25), with an explicit assertion that no client appears on both sides of the split. A random (non-grouped) split was also run for comparison, to make the size of the leakage risk visible rather than assumed — see Results.

Leakage audit

Every feature above was checked against the standard leakage questions (calculated only within the feature window; no product-decision output used as a feature; no derived field secretly encoding the label). One field, trend_pct, was deliberately added and removed as a demonstration: because it is the raw quantity the label is bucketed from, including it inflates AUC toward ~1.0 — a circular result, not a discovery — and it is excluded from every model reported here.

06 · Limitations & Honest Framing

What this can and cannot claim

Proxy label, not a future outcome

The decline label is read from the same window as the features. Results describe association within that window — not a forecast.

Observational, not causal

No experiment was run. Nothing here shows a refresh causes recovery — only that certain signals are observed alongside decline.

One month, one lane's slice

Built and validated on 2026-03 only, against ~104 pseudonymized clients. Not tested on the sealed final month or across seasons.

Look-alikes not ruled out per row

Consolidation, seasonality, and SERP-level click loss can all resemble "decline" in this data and are not individually verified for every flagged page.

Every claim in this paper uses observed, measured, directional, or decision-support language on purpose. No claim here states or implies a Google algorithm factor, a proven causal refresh effect, or a guarantee of any individual page's future performance.

07 · Ranked Recommendations

The action playbook

Pages are scored, banded into three archetypes, and mapped to one action each. Every high_priority_review row requires human review before any change — this queue orders attention, it does not execute anything.

  1. high_priority_review → review_for_refresh
    score band ≥ 80th percentile · reason codes: model_decline_risk, stale_underperforming_ctr, page_one_decay_risk · FILL: n rows
  2. watch → monitor
    score band 40th–80th percentile · spot-check only · FILL: n rows
  3. low_priority → no_action
    score band < 40th percentile · no review this cycle · FILL: n rows

What should NOT be automated

  • Auto-publishing, auto-rewriting, or auto-deleting any page from this score alone.
  • Treating a low score as a permanent clearance — re-score on a monthly cadence.
  • Feeding this score into another automated system without a human decision in the loop.
  • Publishing any client-identifying detail from the underlying queue externally.

Monitoring & retrain triggers

Re-run monthly; treat a >20% month-over-month shift in the high-priority band's size, or a reviewer false-positive rate above roughly 1-in-5 on that band, as a signal to re-inspect feature distributions before trusting the next queue. Retrain at most monthly, always under the same client-grouped validation discipline used here — never skipped to save time.
